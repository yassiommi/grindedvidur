KV Storage & Sharing

When sharing is on and KV lives on SSD, the local shard can be read either as scattered per-token I/Os (each 512 B unit counts against the IOPS cap) or coalesced into large sequential transfers — merging collapses IOPS to ~1 read/layer so the cost becomes pure bandwidth. Merging is optimistic: top-k positions are scattered, so true coalescing implies reading the shard sequentially (possible over-read) rather than gathering exact tokens.

Per-layer compute model (ms — raw / before TP. defaults: FP8 + MLA absorption)
Compute model: cmp = (sh_flat + sh_perbs · BS) / TP + un_flat + un_perbs · BS. Defaults calibrated for FP8 + MLA absorption against analytical_layer.py across BS=1–32, TP=1–8. For FP16 multiply all four by ~2.
These are compute-only per-layer times. The model uses F = max(io_F, compute_F) and S = max(io_S, compute_S) where compute = block_a + topk + attn + moe (S drops topk). TP-shard the compute by dividing by TP if you want a per-rank view; defaults assume already-sharded.

Model — quick reference

kv_io = max( kv_bytes / SSD_BW , kv_iops / SSD_IOPS , SSD_FLOOR ) — whichever of bandwidth, IOPS, or floor is the binding constraint dominates.
F = max(idx_io + kv_io, compute_F) — F-layer IO chain is idx_io → topk → kv_io; we sum the IO and take the max against compute.
S = max(kv_io, compute_S) — S-layer reuses prior F's top-k, no indexer IO of its own.
TPOT — walked across PP stages: stage 0 advances layer-by-layer where compute waits on cumulative IO; each later stage's IO can overlap with the previous stage's compute, then its compute is added on top. Matches the analytical model's pipeline schedule.
Forward mode is direct. Reverse modes binary-search over the unknown until TPOT matches the target.
